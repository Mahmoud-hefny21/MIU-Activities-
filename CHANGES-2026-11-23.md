## 1. Committee heads sign in with Google (no password)

**Before:** adding a committee head (admin page or president's dashboard) required an "Initial password" of 12+ characters. The president then had to share that password with the head.

**After:** you enter only the head's MIU Google email (`@miuegypt.edu.eg`) and committee. The head signs in with Google straight away. Nobody creates or shares a password. Heads now work the same way as presidents and supervisors.

Details:
- Head emails must end in `@miuegypt.edu.eg`. Existing heads with other emails keep working; the check applies only when adding a head or changing an email.
- Changing a head's email unlinks the old Google account and signs out the old person's sessions.

## 2. One person can be head in several clubs

**Before:** adding a head refused any email that already had an account, with *"That email already has a club portal account."* So one person couldn't be head in two clubs, or be head in one club and president of another.

**After:** a head is a role on the person's account, one per club. One MIU Google account can:
- be committee head in many clubs (one committee per club);
- keep any other roles it already has.

The person picks the club from the existing dashboard switcher.

Details:
- Removing a head from one club keeps their other clubs and roles. The account is deleted only when its last role is removed.
- The "Staff accounts & roles" page also accepts more than one head role on an account (one per club).
- Admin "Committee heads" page: each row is one club. Edit and remove act on that club only.

## 4. Attendance tasks appear only for assigned students

**Before:**
- Every student saw an "Assigned attendance tasks" button on their QR page, even with no task.
- The button went straight to the scanner. The scanner lists only tasks already accepted, so a new task never showed and couldn't be accepted.
- The dashboard's "Attendance" tasks menu item and overview card showed for every student.
- MIU usher tasks lived on a separate page linked from the header.

**After:**
- **Regular students** see only their QR. No task buttons or task sections anywhere.
- **Students assigned a club task or an MIU usher task** see it only in their dashboard's **Attendance** section, with Accept request → Take my attendance → Open attendance scanner. Both kinds of task are in one list.
- A student who opens the old usher-task page is sent to their dashboard instead. Staff accounts (which have no student dashboard) still use that page and its header link.

## 5. Events with registration turned off

**Before:** the QR and the scanner always required a registration. For an event published with registration turned off, nobody could check in.

**After:**

| Event setting | Who can check in |
|---|---|
| Registration on | Only students who registered |
| Registration off, all-university | Any student |
| Registration off, members only | Only that club's members |

Today's and upcoming no-registration events that a student may attend now appear in their QR page's event list.

The QR rules are unchanged: it refreshes every 15 seconds, works only for the student's own account on their own device, and records attendance once per event.

## 6. Bug #14 — "Validate scanned code" did nothing (fixed, not pushed yet)

Page: Event attendance & capacity (scanner), the "Camera unavailable? Use an attendance code image or scanned text" section.

**Before:**
- With no event selected (the "Assigned event" box empty, as in the bug report), clicking the button did nothing and showed no message. Nothing reached the server.
- Sending the same code again within 4 seconds was silently ignored. That guard exists for the camera, which reads one QR many times a second, but it also blocked typed codes.
- The box was cleared before the result came back, so a failed code had to be pasted again.
- No loading state; the button could be clicked several times.
- Codes pasted with line breaks or spaces were sent as-is and rejected.

**After:**
- No event selected → a red message: "Choose the assigned event first, then validate the code." If the account has no assigned events: "No events are assigned to your account, so codes cannot be validated here."
- Empty box → "Paste the scanned attendance code first."
- Spaces and line breaks are removed from the pasted code before sending.
- The button shows "Validating…" and is disabled until the server answers, so it can't be submitted twice.
- The code is always checked by the server for the selected event. The result is shown in the same green, yellow or red box as the camera: checked in, already checked in, device already used, invalid code, expired code, wrong event, not registered, or not eligible.
- Attendance is recorded only by the server; there is no browser-only success message.
- Event totals refresh after a successful check-in, without reloading the page.
- The box is cleared only after the server answers. On a connection error the code stays so it can be re-sent.
- A typed code can be re-sent straight away.

Also: the admin dashboard's scanner now loads the new version of the scanner script instead of an old cached copy.

Tested by `tests/scanner-manual-code.test.js`: no event, a pasted code with spaces, an invalid code, an immediate re-send, and an empty box. The server-side checks (duplicate, expired, wrong event, device, registration) are covered by the existing attendance tests. Not yet tried on the live site.

## Attendance rules (agreed today)

- Every regular student has their own QR (refreshes every 15 seconds, one account and device, one check-in per event).
- Presidents, IT committee heads and assigned members use the scanner. They also take their own attendance with "Take my attendance"; scanning your own QR is refused.
- Tasks appear only in the assigned student's dashboard.
- Members-only events: only the club's members can be scanned. All-university events: any student.
- Registration on: only registered students. Registration off: no registration needed.
- Ushers scan according to their event's audience and registration setting.

## Problems found (not fixed unless stated)

1. **Frontend CSS check fails, and did before today's changes.** `npm run check:frontend` reports `base.css` out of date, because `base.css` has been edited directly in the past. Rebuilding from source would undo those edits. The live site is unaffected (Vercel uses the committed `base.css`). Today's new CSS rule was added to both `base.css` and its source.
2. **Your local `.env` uses SQL Server; production uses MongoDB.** `DATABASE_PROVIDER=sqlserver` in `.env` sends scripts to a local SQL Server. Scripts meant for the live database must be run with `DATABASE_PROVIDER=mongodb`.
3. **Two IT heads in one committee (MIU-MUNAL).** The site shouldn't allow this; it came from older data. Fixed for MIU-MUNAL IT; other clubs and committees may have duplicates too.
4. **Misspelled and demo accounts in live data:** `rozan24706403@…` and `head.it@miu.edu` (deleted). There may be others.
5. **A test account holds every role in production:** `abdelrahman.zidan@miuegypt.edu.eg` (Software Development, president, vice president, supervisor, PR, English, Security, SSO, Dean, MIU Events). Worth reviewing.
6. **Committee lists are cached by the live server.** After changing the database directly, application forms and member pages show old committee names until the server restarts or the site is redeployed.
7. **A committee head only sees members and applications whose committee name matches theirs exactly.** Renaming a committee moves its applications too.
8. **Attendance tasks show only on the event day.** A task for a later date doesn't appear in the dashboard yet.
9. **Events from before the registration setting existed still require registration.** Only events explicitly set to registration off admit everyone.
10. **Vercel logs are kept for only 1 hour** (Hobby plan), so older errors can't be investigated.
11. **In the Bug #14 screenshot, the "Assigned event" box was empty.** That means the signed-in account had no event it could scan: no accepted task, not the president or IT head of the event's club, not an assigned supervisor. The button now says so. For a real check-in, use an account assigned to that event.
